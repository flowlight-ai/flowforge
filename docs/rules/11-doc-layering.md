## 11.1 三顶层文档一一对应（SRS/SAD/SDD）

每个项目的 `docs/` 顶层**必须且仅必须**包含以下三份顶层文档，按软件工程 SRS→SAD→SDD 标准流程依次开发：

| 顶层文档 | 软件工程标准 | 开发依据 | 内容范围 | 大小上限 |
|---------|------------|---------|---------|---------|
| `spec.md` | 需求规格说明书（SRS） | 用户指令 + VISION + review | **核心关键功能**需求规格 + 0层架构需求 | ≤ 3000 行 |
| `arch.md` | 架构设计说明书（SAD） | spec.md + features/ | **核心关键功能**架构设计 + 0层架构 | ≤ 3000 行 |
| `design.md` | 详细设计说明书（SDD） | spec.md + arch.md + features/ + architecture/ | **核心关键功能**详细设计 | ≤ 3000 行 |

**SRS/SAD/SDD 标准章节模板**（详见 `prompts.md` P51/P52/P53）：

- **SRS（spec.md）**：§1 引言 / §2 总体描述 / §3 具体需求-核心 / §4 外部接口 / §5 非功能需求 / §6 历史背景资料
- **SAD（arch.md）**：§1 引言 / §2 架构总览 / §3 核心组件设计 / §4 接口设计 / §5 数据设计 / §6 部署架构 / §7 历史背景资料
- **SDD（design.md）**：§1 引言 / §2 系统结构 / §3 模块详细设计-核心 / §4 接口详细设计 / §5 数据结构 / §6 运行设计 / §7 历史背景资料

**三顶层文档必须一一对应**：同一核心功能在 spec.md/arch.md/design.md 中必须**章节同号**（如 §3.2 CapabilityProfile 在三个文档中都是 §3.2），引用通过 `[doc:spec.md#3.2]` / `[doc:arch.md#3.2]` / `[doc:design.md#3.2]` 互链。

## 11.2 三子目录 F0XX/A0XX/D0XX 一一对应（feature 级）

非核心功能 / 单一 feature 的需求规格、架构设计、详细设计**必须**拆分到三个对应子目录，编号一一对应：

| 子目录 | 用途 | 文件命名 | 模板 |
|--------|------|---------|------|
| `features/` | Feature 级 SRS | `F0XX-kebab-case.md` | `features/TEMPLATE.md` |
| `architecture/` | Feature 级 SAD | `A0XX-kebab-case.md`（与 F0XX 同号） | `architecture/TEMPLATE.md` |
| `design/` | Feature 级 SDD | `D0XX-kebab-case.md`（与 F0XX 同号） | `design/TEMPLATE.md` |

**铁律**：每个 feature 必须三份齐全（F0XX + A0XX + D0XX 同号），缺一即文档不完整。

**单文件大小**：≤ 50KB（灵智体可在单次任务中完整重写）。

## 11.3 三阶段开发流程（不可颠倒）

```
阶段1 spec.md（SRS）→ 阶段2 arch.md（SAD，基于 spec + features）→ 阶段3 design.md（SDD，基于 spec + arch + features + architecture）
```

- 阶段1完成后才可进入阶段2（架构设计必须基于需求规格）
- 阶段2完成后才可进入阶段3（详细设计必须基于架构设计）
- 阶段3完成后写反思到 生态规范大全原件 + `prompts.md`

## 11.4 V7.0 合并纪律（V7.0→V7.1 强制要求）

- ✅ **合并 = 抽取 V7.0 历史章节中的有效设计契约，逐章节融入 V7.1 增补章节对应位置**
- ❌ 合并 ≠ 归档到 `_archive/`（归档只是清理过程文档，不等于合并）
- ❌ 合并 ≠ 字符串替换（必须逐章节理解 V7.0 设计意图后融入 V7.1）
- **V6.0 历史章节保留**为背景资料，明确标注 `[v6.0 历史内容]`
- **V7.0 历史章节标注** `[v7.0 历史章节 — 待逐章节合并到 v7.1]`，合并完成后整体移到 `_archive/v70_merged/`
- **过程文档、审核记录、历史快照**统一放到 `_archive/` 或 `face/` 目录，**禁止**放在 spec.md/arch.md/design.md 顶层

## 11.5 9 大点名称修订贯穿全程（铁律）

文档重构过程中**必须同步**完成 9 大点名称修订（详见命名契约文档）：

1. **灵智体定义**：去 AGI/去虚幻用语，使用 AI 业界概念（General-Purpose Agent / Embodied AI / Character AI 等）
2. **12 核心概念**：中英文 + AI 业界概念三标注
3. **进化阶/觉醒阶**：中英文 + AI 业界概念三标注
4. **魂忆→灵忆 / 魂印→灵印**：全局术语替换
5. **AI 术语优先**：代码与对外文档使用 AI 专业术语，体系名（灵智/养灵等）仅用于社区社交
6. **弱化"万物"**：对外宣称用"智能体自进化框架"或"多形态可进化智能体（Evolvable Agent）"，"可进化智能体"仅用于内部体系
7. **责任方名称**：使用名著/童话/神话/游戏物种（架构师=猫头鹰鲁班 / 审查=猎犬夏洛克 / 设计=孔雀梵高 / 文档=钢笔 / 测试=蜜獾）
8. **forgemind 应用层**：明确定位为平台应用层（育公共通用灵智体）
9. **三方 Agent 集成强化**：Claude Code/Codex/OpenCode/Trae + EAC 七契约 + 六层 Guardrails

## 11.6 文档开发纪律（违反即作废）

1. **逐章节理解后修改**：每个章节单独子任务（≤500行），禁止批量字符串替换
2. **每个文件分配子任务**：大文件按章节拆分，每个子任务有明确的输入/输出/验收标准
3. **真相源唯一**：每个概念只有一个真相源文件，其他文件用 `[doc:文件名#章节]` 引用
4. **保留有效内容**：去重去冗余但不删除已有有效设计契约
5. **顶层文档不冗余**：核心放顶层，非核心放子目录，过程文档移 `_archive/`
6. **ADR 不可变历史**：决策变更通过新增 ADR 引用旧 ADR，不修改旧 ADR
7. **operator 愿景锚点不可改**：VISION §7 的 7 条原则不能被 Forgekin 修改

## 11.7 文档自我演进规则

1. 文档更新必须由 Eval 信号触发（不能主动修改）
2. 保留 `[doc:引用]` 格式
3. 单文件 < 50KB（feature 级）/ ≤ 3000 行（顶层文档）
4. 不违反 VISION §7 operator 愿景锚点
5. 不修改 ADR（ADR 不可变）
