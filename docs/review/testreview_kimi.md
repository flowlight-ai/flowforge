## 二、致命缺陷 (P0 — 必须修复)

### P0-1: 全量测试用例零真实执行记录，仍是"纸面测试"

**位置**: 全文档

**问题**: v8.0 虽然提供了 `conftest_e2e.py`、`TestMetricsCollector`、`assert_metrics` 等可执行代码，但**整个 test.md 没有任何一个测试用例被实际执行过**的证据：

1. **指标记录模板所有实际值都是 `_`**（第二章2.2节、第十六章各Workflow指标记录表）
2. **附录A报告模板所有状态栏都是 `-`**（L2563-L2637）
3. **B.4修复追踪表所有修复状态都是 `⏳ 待修复`**（L2678-L2681）
4. **没有发现任何真实执行后的日志、截图、指标JSON**

**影响**: 这是"版本上线后发现一堆问题"的根因。测试用例设计得再完美，没有真实执行过就等于零。

**修复要求**:
1. **立即执行 Phase 0 代码修复**（B1-B4）
2. **执行 Phase 1 模型通道健康检查**，记录真实延迟和可用性
3. **至少执行 IT-WF-API-01（deep_article）一次真实端到端测试**，填写指标记录表
4. **至少执行 IT-SOLO-02（写作意图）一次真实Solo UI测试**，验证WebSocket事件序列
5. **附录A报告模板必须基于真实执行结果填写**

---

### P0-2: IT-WF-API-02~08 缺少调用路径验证表和预期输出JSON结构

**位置**: 第十六章 IT-WF-API-02~08 (L820-L1191)

**问题**: 修订项8和9仅对IT-WF-API-01落地，其余7个Workflow用例仍然缺少：
1. **调用路径验证表** — 无法验证Agent内部工具调用顺序

这是6份专家审核的共识问题（5/6审核人指出），v8.0仅部分落地。

**影响**: 7个Workflow的测试即使"通过"也无法证明调用路径正确、输出格式完整。

**修复要求**: 为IT-WF-API-02~08每个用例补充：
- 调用路径验证表（同16.1格式）
- 预期输出JSON结构（同16.1格式）
- Memory指标验证（同16.1格式）

## 三、严重缺陷 (P1 — 强烈建议修复)

### P1-1: MetricsCollector Memory/WebSocket/Frontend维度仍为占位符

**位置**: 第二十八章 (L2116-L2361)

**问题**: `TestMetricsCollector.generate_report()` 中：
- `memory.compactions` 硬编码为 `0`（需要从`context.warning`事件采集）
- `memory.cache_hit_rate` 硬编码为 `0`（需要从cache工具结果采集）
- `websocket.sequence_gaps` 硬编码为 `0`（需要检查序号连续性）
- `frontend.timeline_nodes` 硬编码为 `0`（需要Playwright DOM计数）
- `frontend.citation_links` 硬编码为 `0`（需要Playwright DOM计数）

**影响**: 28项指标中仅19项可自动采集，剩余9项为占位符，无法完整验证测试质量。

**修复要求**:
1. Memory压缩触发次数：订阅`context.warning`事件，统计92%阈值触发次数
2. 缓存命中率：在`_on_tool_end`中检查cache工具返回的`cached`字段
3. WebSocket序号连续性：在`_on_event`中检查事件序号差值
4. Frontend指标：提供Playwright辅助函数，在测试结束后采集DOM数据

---

### P1-2: Solo UI路径IT-SOLO-02~08缺少完整WebSocket事件序列

**位置**: 第十七章 IT-SOLO-02~08 (L1230-L1432)

**问题**: IT-SOLO-01有完整的5行WebSocket事件序列，但IT-SOLO-02~08仅IT-SOLO-02列出了部分事件序列，其余用例完全没有。

**影响**: 无法验证Solo UI路径的事件完整性，无法检测事件丢包和序号跳号。

**修复要求**: 每个Solo UI用例必须列出完整的预期WebSocket事件序列，至少包含：
1. `solo.stage.enter/exit` 事件（每个阶段）
2. `solo.tool.start/end` 事件（每个工具调用）
3. `solo.llm.start/end` 事件（每个LLM调用）
4. `solo.draft.update` 事件
5. `solo.task.completed` 事件

### P1-4: "测试通过"7维定义缺少量化阈值和自动化断言映射

**位置**: 第三章 (L278-L289)

**问题**: 7维"测试通过"定义是定性描述，缺少与MetricsCollector的自动化断言映射：
- "所有预期阶段按序执行" → 没有说明如何验证（`workflow.step.start`序号差值=1？）
- "每个Agent的LLM调用次数符合预期" → 没有说明如何计数（监听`llm.start`事件？）
- "前端时间线正确渲染" → 没有说明如何验证（Playwright DOM计数？）

**修复要求**: 为每个维度补充：
1. 量化阈值（如：阶段顺序误差=0，LLM次数在[min,max]范围内）
2. 自动化断言代码（使用`assert_metrics`函数）
3. 失败时的调试信息输出

---

### P1-5: 缺少"测试不通过"的明确定义和失败处理流程

**位置**: 全文档

**问题**: test.md 只定义了"测试通过"，没有定义"什么情况下必须中止测试"、"失败后如何调试"、"失败后如何记录问题"。

**影响**: 测试执行时遇到失败，测试人员不知道：
- 是继续执行后续用例还是立即停止？
- 失败原因是代码Bug、模型问题、Prompt问题还是环境问题？
- 如何记录失败信息（日志、截图、指标JSON）？

**修复要求**: 新增"测试失败处理规范"：
1. P0失败（代码Bug）→ 立即停止，记录堆栈和上下文
2. P1失败（模型不可用）→ 跳过该通道，继续其他通道
3. P2失败（Prompt问题）→ 记录到prompt_issues.md，继续执行
4. 所有失败必须输出：失败原因、相关日志片段、MetricsCollector报告、建议修复方案

## 四、一般缺陷 (P2 — 建议修复)

### P2-1: 缺少LLM输出内容质量指标

**位置**: 第二章 (L225-L259)

**问题**: 28项指标中缺少"LLM输出内容质量"维度：
- 字数达标率（draft长度是否达到预期）
- 关键词命中率（SEO关键词是否出现）
- 事实准确率（fact_check验证通过比例）
- 格式合规率（JSON/XML输出是否符合schema）

**修复要求**: 新增"内容质量"维度指标：
- `content.word_count` — 实际字数/预期字数
- `content.keyword_hits` — 目标关键词出现次数
- `content.fact_accuracy` — fact_check验证通过比例
- `content.format_compliance` — 输出格式符合schema的比例

---

### P2-2: 缺少工具调用失败率的按工具分类统计

**位置**: 第二章 (L236-L239)

**问题**: `tool.success_rate` 是全局成功率，没有按工具分类统计。无法定位是哪个工具经常失败。

**修复要求**: `tool.by_name` 中增加每个工具的成功率：
```python
"tool": {
    "by_name": {
        "web_search": {"calls": 10, "success": 8, "rate": 0.8},
        "opensieve_search": {"calls": 5, "success": 2, "rate": 0.4},
    }
}
```

### P2-3: 缺少模型通道自动关闭机制

**位置**: 第十六章16.0节 (L686-L712)

**问题**: test.md 要求"验证没有通过的API模型请通过配置暂时关闭"，但没有提供自动化机制。测试人员需要手动修改`models.yaml`。

**修复要求**: 提供自动化脚本：
```python
# tests/scripts/auto_disable_failed_models.py
# 测试后自动将失败的模型通道设置为 enabled: false
```
