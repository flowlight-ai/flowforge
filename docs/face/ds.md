# ContentForge / DevForge 下一代需求规格说明书

> 版本: vNext-1.0 | 日期: 2025-07-14  
> 基于: FlowForge v4.0 + 多厂面试反馈 + 行业前沿痛点  
> 定位: 从“高级Agent行为生产流水线”进化为**具备记忆真相治理、多Agent协作决策与自进化的Agentic Work OS**

---

## 一、总体判断：行业已经到了下一阶段

过去半年，我在面试中反复听到的核心信号是：**业界已经不满足于“Agent能做什么”，而是在追问“Agent系统凭什么可信、可控、可进化、可规模化”**。这正好是我们FlowForge v4.0已经打下基础、而需要进一步突破的方向。

六大公司（阿里、腾讯、字节、小米、高德、深信服）的面试题面可以归纳为九个能力维度的深度追问，而不是简单的功能列表。下面我把这些追问直接翻译成我们的新需求。

---

## 二、九大能力维度的需求规划

### 维度1：记忆治理与真相管理

**业界痛点**：面试官反复追问“记忆的权威如何定义”、“冲突时怎么办”、“低权威如何晋级”、“过期如何退役”。这说明他们已经被“堆向量库”坑过了——记忆系统如果没有治理机制，Agent的行为会随着时间推移变得越来越不可预测。

**我们的新需求**：

| 需求ID | 功能 | 详细说明 |
|--------|------|---------|
| MEM-01 | **记忆权威分级** | 每条记忆必须标注权威等级：`observed`（观察到的聊天内容）、`inferred`（Agent推断的结论）、`verified`（经人工确认的）、`architectural`（已固化为架构决策的）。不同等级的记忆在检索、引用和冲突处理时的权重不同 |
| MEM-02 | **记忆晋级与退役机制** | 低权威记忆在满足条件（如被3次以上任务成功引用、经人工确认等）后自动晋级；过期记忆（如基于已废弃API的代码模式）自动标记为`retired`，不再被检索但保留审计追溯 |
| MEM-03 | **冲突仲裁引擎** | 当两个Agent写入矛盾结论时，系统根据`来源权威 > 时间新旧 > 证据链长度 > 人工裁决`的优先级自动仲裁，并保留冲突记录供审查 |
| MEM-04 | **五层记忆架构落地** | 工作记忆（当前任务状态）→ 短期记忆（会话上下文）→ 长期记忆（持久化事实与经验）→ 语义记忆（向量化知识库）→ 情景记忆（成功/失败的任务轨迹），每层有独立的存储、检索、生命周期和治理策略 |
| MEM-05 | **Shared State边界定义** | 明确shared state是“Agent协作账本”——记录任务分解、当前持有者、接口契约和决策依据，而不是简单的全局变量。与长期记忆和知识库的边界清晰 |

---

### 维度2：Multi-Agent协作、路由与终止条件

**业界痛点**：面试官最怕的不是Agent不聪明，而是“Agent互相瞎聊停不下来”、“拉新Agent的决策莫名其妙”、“没有状态机怎么保证不漂移”。这其实是FlowForge的Workflow模式已经解决了的问题，但需要进一步显式化。

**我们的新需求**：

| 需求ID | 功能 | 详细说明 |
|--------|------|---------|
| COL-01 | **首接Agent路由协议** | 定义“第一个接球的Agent”的选择规则：任务分类器根据意图类型路由到对应专业Agent，闲聊由通用Agent承接，复杂任务由Orchestrator拆解后分发。路由决策可审计 |
| COL-02 | **动态拉入新Agent的决策门** | 不是让Agent“觉得需要就叫”，而是设置Gate条件：当前Agent声明的能力capability不覆盖任务所需 → 查询Agent Registry → 匹配最优Agent → 发出邀请。过程有日志 |
| COL-03 | **终止条件配置化** | 防止无限对话的硬机制：最大对话轮数、工具调用进展停滞检测、任务完成信号、外部超时事件。每种终止条件可独立启用和配置 |
| COL-04 | **A2A协议标准化** | 基于FlowForge的Agent执行接口，定义标准A2A消息格式（任务描述、预期产出、接口契约、证据要求）。兼容Google A2A标准，同时支持我们自己的扩展 |
| COL-05 | **球权与契约机制** | 任务分解后，每个子任务明确“当前持有者(holder)”、“预期交付物(deliverable)”、“截止条件(completion criteria)”。交接时验证交付物，不满足则退回 |

---

### 维度3：Harness、Skill与自进化

**业界痛点**：面试官反复问“自进化具体怎么实现”、“Skill如何从真实任务长出来”、“经验沉淀到哪里”。这说明他们需要的是可审计、可回滚、可度量的进化路径，而不是“让模型反思一下”的黑盒。

**我们的新需求**：

| 需求ID | 功能 | 详细说明 |
|--------|------|---------|
| EVO-01 | **三层Harness架构** | **软层（Skill/Convention）**：可配置的规则、提示词模板、工作流定义；**硬层（Gate/Validator）**：Schema校验、权限检查、参数预检——让错误请求在进入Agent loop之前就失败；**Eval层**：回归测试套件、质量门槛、漂移检测 |
| EVO-02 | **Skill从任务中自动提取** | 当同一类任务的解决模式重复出现N次（可配置阈值），系统自动生成Skill草案，经人工审核后发布到Skill库。附带使用统计和效果指标 |
| EVO-03 | **经验按风险逐级固化** | 成功经验先写入Memory（可随时覆盖）→ 经多次验证后升为Convention（软约束，Agent偏离时告警）→ 再经严格测试后升为Gate规则（硬拦截）。进化路径清晰可追溯 |
| EVO-04 | **事故驱动护栏** | 每次任务失败或Agent行为异常时，自动分析根因，生成护栏规则草案。经人工确认后生效，防止同类问题再次发生 |
| EVO-05 | **自指修改的防漂移机制** | Agent可以修改自己的Harness配置，但修改必须经过Eval回归测试 + 人工审批 + 灰度发布。任何修改都保留完整审计记录 |

---

### 维度4：Eval、Benchmark与模型选择

**业界痛点**：面试官不再只问模型Benchmark，而是追问“Agent系统级评测怎么做”、“如何证明改了Harness更好”、“换模型如何评估ROI”。这说明行业已经过了“跑个MMLU就敢上线”的阶段。

**我们的新需求**：

| 需求ID | 功能 | 详细说明 |
|--------|------|---------|
| EVAL-01 | **全维度Eval框架** | 覆盖A2A（消息格式正确率、任务交接成功率）、Memory（召回率、冲突率、晋级准确率）、Tracing（步骤完整性、错误定位准确性）、Skill（使用频率、任务缩短率） |
| EVAL-02 | **回归测试套件自动生成** | 每次Harness修改后，自动运行预设的“金标准任务集”并对比新旧结果，检测能力漂移 |
| EVAL-03 | **模型升级的ROI评估** | 预定义评估维度（生成质量、响应速度、成本、特定任务成功率），在新模型上跑Eval套件，输出对比报告 |
| EVAL-04 | **带真实工具的虚拟Eval环境** | 构建沙箱化的测试环境，包含真实API mock、文件系统、权限限制和故障注入，用于长程任务的端到端评测 |
| EVAL-05 | **评估复杂度分层** | 对普通用户只展示“通过/不通过”和质量趋势，对高级用户和开发者展示完整Eval数据和可解释性报告 |

---

### 维度5：工程交付、质量与复杂代码仓

**业界痛点**：小米、深信服、腾讯都深入追问了大型代码仓、多人协作、需求变更、回归测试、多仓依赖等工程化问题。Agent如果不能融入真实开发流程，就只能停留在Demo阶段。

**我们的新需求**：

| 需求ID | 功能 | 详细说明 |
|--------|------|---------|
| ENG-01 | **Git Worktree集成** | 每个Agent任务在独立的Git worktree中执行，互不干扰。完成后由Review Agent检查变更，通过后合并 |
| ENG-02 | **依赖图分析引擎** | 分析代码仓的模块依赖关系，生成影响分析报告。Agent修改代码时自动评估影响范围 |
| ENG-03 | **Spec-Driven Development (SDD)** | 需求先以结构化Spec形式定义（功能描述、验收标准、接口契约、测试用例），Agent按Spec实现，Eval按Spec验收 |
| ENG-04 | **需求变更的联动更新** | Spec变更时，自动触发生成新的实现计划、更新测试用例、标记受影响的已有代码，保持一致性 |
| ENG-05 | **多Agent并行开发锁与冲突解决** | 多人/多Agent并行开发时，系统按模块/文件粒度自动加锁；冲突发生时提供三方合并工具和人工裁决界面 |
| ENG-06 | **测试Agent专用角色** | 独立的测试Agent：根据Spec生成测试用例、执行回归测试、分析失败原因、生成修复建议。不作为开发Agent的子模块 |

---

### 维度6：架构定位与产品差异化

**业界痛点**：面试官反复问“最突出的两个架构设计”、“与Claude Code/CrewAI/OpenClaw的核心差异”、“是通用Agent还是Coding Agent”。这说明他们需要清晰的定位和真实的差异化。

**我们的新需求**：

| 需求ID | 功能 | 详细说明 |
|--------|------|---------|
| ARC-01 | **公开架构决策记录（ADR）** | 每个重大架构决策都有文档记录：背景、备选方案、选择理由、预期后果。作为Memory中`architectural`权威等级的来源 |
| ARC-02 | **Shared State白皮书** | 明确定义Shared State的范围、生命周期、访问控制、与长期记忆和知识库的边界。作为项目核心差异化文档 |
| ARC-03 | **与竞品的逐项对比矩阵** | 按功能维度（记忆治理、协作模式、自进化、Eval、工程集成等）与Claude Code、CrewAI、OpenClaw、LangGraph等做客观对比 |

---

### 维度7：企业治理、组织知识与规模化Adoption

**业界痛点**：小米和深信服最关注的是“从个人到千人团队后，系统怎么不崩塌”。组织知识管理、平台与业务的分工、合规审计、跨团队协作——这些是Agent系统从“个人工具”到“企业平台”必须跨越的鸿沟。

**我们的新需求**：

| 需求ID | 功能 | 详细说明 |
|--------|------|---------|
| ENT-01 | **组织知识分层管理** | 个人级（偏好、习惯、个人Skill）→ 项目级（代码规范、架构约定、接口契约）→ 部门级（技术栈最佳实践、安全策略）→ 公司级（合规要求、通用Workflow）。每层有独立的权限和生命周期 |
| ENT-02 | **最佳实践自动挖掘** | 从大量成功任务的执行轨迹中，自动识别高频模式、高效路径和常见错误，生成组织级Skill和Convention |
| ENT-03 | **平台与业务定制边界** | 平台团队提供核心引擎（FlowForge）+ 通用Agent/Tool库 + 治理框架；业务团队在此基础上定制自己的Agent、Skill、Workflow和Eval |
| ENT-04 | **多租户与凭证管理** | 企业环境下，不同团队、不同项目的Agent必须隔离运行；对接外部系统（飞书、GitHub、Jira等）的凭证按租户独立管理 |
| ENT-05 | **合规审计与追溯** | 所有Agent决策、工具调用、代码变更都有完整审计日志，支持按任务、时间、执行者、影响范围查询，满足企业合规要求 |

---

### 维度8：用户价值、商业化与未来工作方式

**业界痛点**：字节和腾讯都问到“是否真的有人使用”、“为什么开源”、“商业化路径”。这说明一个Agent框架要持续发展，必须有真实用户和清晰的成长路径。

**我们的新需求**：

| 需求ID | 功能 | 详细说明 |
|--------|------|---------|
| USR-01 | **用户使用数据分析** | 统计Agent的使用频率、任务类型分布、成功率、用户留存、NPS等指标。为产品迭代提供数据支撑 |
| USR-02 | **开源社区建设** | 公开GitHub仓库（含完整README、架构文档、贡献指南、Roadmap）；建立Discord/飞书社区；定期发布Release Notes |
| USR-03 | **云端/本地双模部署** | 本地版保护隐私（Memory、凭证、代码都在本地）；云端版提供24×7常驻、弹性计算、多端访问。两者可无缝切换 |
| USR-04 | **未来工作方式愿景** | 人定义问题、设检查点、审批风险；Agent负责调研、实现、测试、部署和日常维护。系统提供从需求到交付的全链路透明度和质量保障 |

---

### 维度9：安全性、沙箱与执行环境

**业界痛点**：阿里和深信服都问到“云端Sandbox怎么做”、“逻辑无状态环境受管”、“成本与隔离的权衡”。代码执行的安全性是Coding Agent商用的前提。

**我们的新需求**：

| 需求ID | 功能 | 详细说明 |
|--------|------|---------|
| SEC-01 | **增强沙箱机制** | 在现有进程级隔离基础上，增加网络隔离（可选白名单）、文件系统写保护、系统调用过滤。支持Docker/Firecracker等容器化沙箱 |
| SEC-02 | **沙箱经济性方案** | 对于简单任务（如代码格式化、静态分析），使用轻量级进程沙箱；对于需要完整环境的重度任务（如编译运行测试），使用按需创建的容器沙箱。支持沙箱复用池 |
| SEC-03 | **凭证安全** | 接入外部系统（GitHub、飞书、数据库）的Token/密钥使用Vault管理，Agent无法直接获取明文，只在沙箱内的安全变量中注入 |
| SEC-04 | **执行环境声明式配置** | 每个Agent/Workflow可以声明所需的执行环境（Python版本、系统包、环境变量、网络权限），系统自动准备对应沙箱 |

## 四、实施优先级建议

| 优先级 | 模块 | 理由 |
|--------|------|------|
| **P0 立即启动** | MEM-01~05（记忆治理） | 这是六家公司全部高频追问的维度，也是我们当前系统最需要补强的短板 |
| **P0 立即启动** | COL-01~05（Multi-agent协作） | FlowForge的Workflow模式已打下基础，只需显式化路由协议和终止条件 |
| **P1 第二批次** | EVO-01~05（自进化）、EVAL-01~05（Eval框架） | 这是行业最前沿的差异化点，也是面试中展现深度的关键 |
| **P1 第二批次** | ENG-01~06（工程交付） | 直接关系Coding Agent的可用性和企业落地 |
| **P2 第三批次** | ENT-01~05（企业治理）、SEC-01~04（安全沙箱） | 规模化和企业级的保障 |
| **P2 第三批次** | ARC-01~03（架构定位）、USR-01~04（商业化） | 支撑开源社区和产品成长 |

---

**总结**：这份需求规格是基于六家顶级公司面试反馈的深度洞察，不是凭空想象的feature list。每一个需求都有真实的业界痛点支撑，都可以直接对照面试题面验证。我们的FlowForge v4.0已经打下了坚实的架构基础，现在要做的就是在这基础上，把记忆治理、协作决策、自进化和企业级能力做到行业标杆水平。
