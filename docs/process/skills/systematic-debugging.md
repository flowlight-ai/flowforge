# 系统化调试（systematic-debugging）

## 触发时机

- **任何**技术问题：测试失败、生产缺陷、意外行为、性能问题、构建失败、集成故障。
- **尤其是**：时间压力大（紧急让猜测变得诱人）、"就一个快修"、已经试过多个修复都没用、你并不完全理解这个问题。

**核心原则**：先找根因再修复。症状修复就是失败。

## 流程步骤

**铁律：没有根因调查就没有修复。** 未完成第一阶段，不得提出修复方案。

### 阶段 1：根因调查

1. **细读错误信息**：不跳过；完整读堆栈；记下行号、文件、错误码——错误信息常常直接含答案。
2. **稳定复现**：可靠触发吗？确切步骤是什么？每次都发生吗？不能复现 → 收集更多数据，不要猜。
3. **检查近期变更**：什么变了可能导致这个？`git diff`、近期提交、新依赖、配置变更、环境差异。
4. **多组件系统取证**（CI → 构建 → 签名、API → 服务 → 数据库）：修复前先在每个组件边界加诊断 instrumentation——记录进出每个组件的数据、验证环境/配置传播、检查各层状态；跑一次收集证据定位**哪一层**断了，再深入那一层。
5. **数据流回溯**：错误在调用栈深处 → 从坏值起源处向上追：谁用坏值调用了它？一路追到源头，修源头不修症状。

### 阶段 2：模式分析

找到同仓库中**能工作的类似代码**；完整读参考实现（不略读）；列出工作版与故障版之间的**每一个**差异（不假设"这个无关"）；理解依赖（组件、配置、环境、假设）。

### 阶段 3：假设与检验（科学方法）

1. 形成**单一**假设并写下："我认为根因是 X，因为 Y"——要具体。
2. **最小化检验**：可能的最小改动、一次一个变量。
3. 检验后判定：成立 → 进阶段 4；不成立 → 形成**新**假设，不在旧修复上叠修复。
4. 不懂就说不懂——不装懂，求助或再研究。

### 阶段 4：实施

1. **先写复现测试**（最简复现；走 `test-driven-development.md` ⑥ 的 RED）。
2. **单一修复**：只修确认的根因；一次一个改动；不带"顺手"改进、不捆绑重构。
3. **验证修复**：测试过了吗？其他测试没破吗？问题真的解决了吗？（⑩ 证据标准）
4. **修复不奏效**：已试 < 3 次 → 回阶段 1 重新分析；**≥ 3 次 → 停，进入第 5 步**。
5. **3+ 次失败 = 架构问题**：每次修复都在别处暴露新的共享状态/耦合、需要"大重构"才能修、每修一处坏另一处——停下质疑架构本身：这个模式根本成立吗？该重构还是继续贴创可贴？**与操作者讨论后再动**。这不是"假设失败"，是"架构错了"。

## 门禁

以下念头出现即**停，回阶段 1**：

| 念头 | 事实 |
|---|---|
| "先快修，回头再查" | 首次修复定调；从一开始就做对 |
| "改下 X 试试看" | 没有假设的修改是盲试 |
| "一次改多处，跑遍测试" | 无法隔离哪个改动起效，还会引入新问题 |
| "跳过测试，我手动验证" | 未测的修复粘不住 |
| "参考实现太长，我改着用" | 部分理解保证出 bug；完整读 |
| "再试一次修复"（已失败 2+ 次） | 3+ 次失败 = 架构问题；质疑模式，别再修 |

95% 的"查不到根因"其实是调查不彻底。

## 与我方规范对接

- **对应状态机**：本资产在 `implement` 阶段内使用；发现的 bug 若阻塞当前任务，遵循 `executing-plans.md`（③）的 STOP 规则上报，不硬闯。
- **调试日志**：与我方"节点耗时统计定位性能瓶颈"的规范一致——多组件取证时同步记录各层耗时，量化定位（用户要求量化时间统计）。
- **T1-T9**：复现测试遵守测试铁律——真实数据（T2）、具体断言（T3）、不 Mock LLM（T1）。
- **根因文化**：与本仓库"主动定位根因而非被动等待"的问题解决规范一致（如曾以"定位具体 LLM 超时根因"替代等待重试）。
- **修复验证**：证据标准见 `verification-before-completion.md`（⑩）；宣称"修好了"前必须跑过复现测试。
