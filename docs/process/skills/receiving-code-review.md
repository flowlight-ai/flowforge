# 接收代码审查（receiving-code-review）

## 触发时机

- 收到任何代码审查反馈之后、实施建议之前——**尤其当反馈看起来不清晰或技术上可疑时**。

**核心原则**：先验证再实施；先问再猜；技术正确性高于社交舒适度。

## 流程步骤

### 响应模式

```
1. 通读：完整读完反馈，不即时反应
2. 理解：用自己的话复述要求（或提问）
3. 验证：对照代码库实际情况核实
4. 评估：对**本代码库**技术上成立吗？
5. 响应：技术性确认或有理由的反驳
6. 实施：一次一项，逐项测试
```

### 不清晰的反馈

任何一项不清晰：**停，先什么都不实施**，就不清晰项请求澄清——条目之间可能相关，部分理解 = 错误实施。

```
操作者："修 1-6"
你理解 1、2、3、6，不清楚 4、5。

❌ 错误：先实施 1、2、3、6，回头再问 4、5
✅ 正确："理解 1、2、3、6。4 和 5 需要澄清后才能动手。"
```

### 分级响应（P1/P2/P3，与 clowder 协议对齐）

| 级别 | 含义 | 响应 |
|---|---|---|
| **P1** | 破坏功能/安全/数据问题的阻断项 | 立即修，其他工作暂停 |
| **P2** | 明确的技术缺陷但不阻断 | 本轮修完再提交，逐项测试 |
| **P3** | 风格/偏好/优化建议 | 评估采纳或记录延后，不阻塞 |

实施顺序（多项反馈）：先澄清全部不清晰项 → 按阻断项 → 简单修复 → 复杂修复；**每项单独测试**，验证无回归。

### 来源区分

- **操作者的反馈**：理解后即可实施（但范围不清仍要问）；不做表演式认同，直接进入动作或技术性确认。
- **外部审查者的反馈**：实施前先核对——对本代码库技术上正确吗？会破坏既有功能吗？现状实现是有原因的吗？全平台可用吗？审查者了解完整上下文吗？疑点用技术理由反驳；无法验证就明说（"没有 X 我验证不了，需要我先调查还是先问？"）；与操作者既有决策冲突时，先停下与操作者沟通。

### YAGNI 核查（"专业化"建议）

```
审查者建议"把它实现规范"时：
  grep 代码库实际使用
  无人调用 → "这个接口没人用。删掉（YAGNI）？"
  有人调用 → 那就规范实现
```

操作者规则："你和审查者都对我负责。不需要的特性，就不加。"

## 门禁

**禁止的响应**：

- ❌ "您说得对！" / "好建议！" / "感谢指出！"——任何感谢或表演式认同（动作本身就是回应：修了、用代码说话）
- ❌ 验证前的"我马上改"
- ❌ 一次实施多项不测试
- ❌ 假设审查者一定对

**反驳错了时**：事实性纠正即可，不长篇道歉、不辩解：

```
✅ "核实了，你是对的——X 确实 Y。现在修。"
```

**何时反驳**：建议破坏既有功能 / 审查者缺上下文 / 违反 YAGNI（无使用者的特性）/ 对本技术栈不正确 / 存在兼容性原因 / 与操作者的架构决策冲突。反驳方式：技术论证、具体问题、引用能跑的测试/代码；架构级分歧交给操作者。

## 与我方规范对接

- **对应状态机**：本资产覆盖 `review` 阶段的反馈侧；审查处置记录落 `docs/process/reviews/`。
- **P1/P2/P3**：分级响应规则来自 clowder 交叉审查协议（P2 层规范），与本资产融合为统一响应协议。
- **质量评审 P33**：与我方质量评审规范（阈值 0.85、5 评委不同模型并行、不达标必须优化不得降阈值）联动——评审结论低于阈值时反馈按 P1 处理。
- **mgr 流程**：反馈修复后的提交经 mgr 走 PR 更新（`mgr sync` / `mgr push --pr`），commit 消息注明修复的审查条目。
- **文档审查**：文档类交付的审查反馈同样适用本资产（用户要求文档开发优先级高于代码，文档反馈不得降级处理）。
