# 需求头脑风暴（brainstorming）

## 触发时机

- 收到任何创造性请求：新增功能、构建组件、添加能力、修改行为——**在写任何代码、搭任何骨架之前**。
- 需求描述还停留在"想法"层面，缺少设计或规格时。

## 流程步骤

### 第一步：分级（三路径）

先分类并**出声宣布**分类结果（让操作者可以纠正）：

| 路径 | 判定标准 | 流程 |
|---|---|---|
| **Spike（探针）** | 可行性问题（"能不能……"），产物是结论而非保留的代码 | 2-3 句话说明问题与探法 → 取得同意 → 以最低成本求证 → 报告建议；产出的任何代码标注"一次性" |
| **Bounded（有界）** | 对**本仓库已有流程**的明确改动（加开关、小接口、单文件修复） | 澄清关键问题 → 在对话中给出简短设计 → **停下等批准** → 批准后走常规开发（TDD 适用），无规格文件 |
| **Architectural（架构级）** | 新项目、新子系统、改变组件接口或依赖关系 | 完整流程：澄清 → 方案 → 分节设计 → 设计文档 → 自审 → 操作者审 → 转入 writing-plans |

**拿不准时走更重的路径**。单向棘轮：任务中途发现的隐藏复杂度只能升路径（停下、说明、升级），不能降。

### 第二步：理解意图（bounded / architectural 共用）

- 先看项目现状（文件、文档、近期提交）。
- 一次只问一个问题（优先选择题）；聚焦目的、约束、成功标准。
- 请求描述多个独立子系统时，先指出需要分解，不要急着细化一个需要拆分的项目；每个子项目走独立的 spec → plan → 实施循环。

### 第三步：探索方案（architectural 路径）

- 提出 2-3 个方案 + 权衡 + 推荐；YAGNI（按需而为）从每个方案中剔除不必要的特性。

### 第四步：呈现设计（architectural 路径）

- 分节呈现，每节按复杂度伸缩（简单几句话，复杂至 200-300 字）；每节确认"到这里对吗"。
- 覆盖：架构、组件、数据流、错误处理、测试。
- 单元划分遵循"单一职责 + 明确接口 + 可独立理解与测试"。

### 第五步：写设计文档（architectural 路径）

- 落盘到 `docs/process/specs/YYYY-MM-DD-<topic>-design.md`。
- **自审**：占位符扫描（TBD/TODO/空节）、内部一致性、范围检查（是否需要分解）、歧义检查（同一需求是否可两种解读）——发现问题就地修复。
- **操作者审查门**：请操作者审阅规格文件，有修改则改后重审；批准前不得进入计划。

## 门禁

**硬门禁（HARD-GATE）**：在向操作者说明意图并取得批准之前，**不得**调用任何实施资产、写任何代码、搭任何骨架——适用于三路径下的**每一个任务**。仪式随任务伸缩，批准门从不伸缩。

"简单任务"反模式自查：

| 念头 | 事实 |
|---|---|
| "太简单不需要设计" | 简单意味着**短**设计（对话中两句话），不是**没有**设计 |
| "标个 bounded 就能跳过规格" | 想用标签省工作本身就是疑虑，走更重的路径 |
| "设计很显然，他们看的时候我就开工" | 门是"批准"，不是"设计长度"；呈现后停下，听到"可以"才动 |
| "我熟悉这类应用，所以是有界的" | bounded 度量的是**仓库**，不是你的熟悉程度；新项目没有已有流程可改，就是架构级 |
| "Spike 能跑，代码就留着吧" | spike 的产物是结论；留代码是新请求，重新分级 |

## 与我方规范对接

- **对应状态机**：本资产覆盖 `requirement → design` 两阶段；`design → plan` 的门禁（designApproved）即本资产"操作者审查门"的机器化。
- **产物分层**：设计文档的内部结构同时遵循静态分层规范（`docs/rules/11-doc-layering` 的 F/A/D 要求）；EP0-2 将提供设计文档模板。
- **术语**：文档用语遵循命名契约（官方 AI 概念名优先）；需求描述涉及智能体时区分"静态智能体/可进化智能体"。
- **收尾**：architectural 路径批准后，唯一合法的下一步是 `writing-plans.md`（②），不得直接进入实现。
