# 完成前验证（verification-before-completion）

## 触发时机

- **任何**完成/成功断言之前；**任何**满意表达之前；提交、建 PR、任务标完成、转下一任务、派发子代理之前。
- 适用于字面表述、改述、同义词、以及**任何**暗示完成/正确的沟通。

**核心原则**：证据先于断言，永远。

## 流程步骤

**铁律：没有新鲜的验证证据，就没有完成宣称。** 本条消息里没跑过验证命令，就不能说它通过。

### 门函数（每次宣称前过一遍）

```
1. 识别：什么命令能证明这个断言？
2. 运行：完整执行（新鲜的、完整的，不是缓存的）
3. 阅读：完整输出 + 退出码 + 失败计数
4. 验证：输出确认断言吗？
   - 否 → 如实陈述实际状态 + 证据
   - 是 → 带证据陈述断言
5. 然后才：做出断言
```

跳过任何一步 = 在撒谎，不是在验证。

### 各类断言的证据标准

| 断言 | 需要的证据 | 不算证据 |
|---|---|---|
| 测试通过 | 测试命令输出：0 失败（如 `pnpm vitest run <路径>` 的 N passed） | 上次跑过、"应该过" |
| 类型干净 | `pnpm typecheck` 退出码 0 | lint 过（lint ≠ 编译器） |
| 构建成功 | 构建命令退出码 0 | 日志"看着没问题" |
| 缺陷修好 | **原症状**的复现测试通过 | 代码改了、假设修好了 |
| 回归测试有效 | 红-绿循环验证：写→过→**还原修复→必须失败**→恢复→过 | 测试跑过一次 |
| 子代理完成 | 检查 VCS diff 亲自核对变更 | 代理报告"成功" |
| 需求满足 | 逐条 checklist 核对（规格/计划逐节） | "测试都过了，阶段完成" |

### 关键模式

**回归测试（红-绿验证）**：写测试 → 跑（过）→ **还原修复 → 跑（必须失败）** → 恢复修复 → 跑（过）。只写不验红的回归测试证明不了任何事。

**子代理委派**：代理报成功 → 查 diff → 亲自核对 → 汇报实际状态。

**需求核对**：重读计划 → 建 checklist → 逐项验证 → 汇报缺口或完成。

## 门禁

以下信号出现即**停**：

- 使用"应该"、"大概"、"看起来"描述工作状态
- 验证前表达满意（"好了！""完美！""搞定！"）
- 未验证就要 commit / push / PR
- 信任代理的成功报告
- 依赖部分验证（部分证明不了任何事）
- "就这一次"
- 累了想收工（疲劳不是豁免）

## 与我方规范对接

- **对应状态机**：本资产覆盖 `verify` 阶段；`verify → finish` 门禁（verificationEvidence）的机器化即本资产——证据（命令、退出码、输出摘要）落盘 `docs/process/verifications/`，状态机拒绝无证据的 finish。
- **T3 联动**："必须有具体断言，不得 status in ('completed','error')"（T3）与本资产"证据先于断言"同源——验证输出必须含具体数字（N passed / exit 0），不接受"跑过了"。
- **T6 联动**：E2E 验证用 MetricsCollector 采集完整指标，证据归档同步含指标快照。
- **量化文化**：与本仓库"各节点量化耗时统计"规范一致——验证证据记录命令耗时，为性能瓶颈定位提供数据。
- **与 ⑫ 衔接**：`finishing-a-development-branch.md` 的第一步"跑全量测试"以本资产为证据标准。
