# 并行子代理调度（dispatching-parallel-agents）

## 触发时机

- 面前有 **2 个以上相互独立**的任务（不同测试文件、不同子系统、不同 bug），且它们：
  - 无共享状态、无先后依赖，可并行推进；
  - 各自的调查/实现互不依赖对方结果。
- 判断依据（依次回答）：任务多吗 → 相互独立吗 → 能并行吗；独立但需顺序 → 顺序派发；不独立 → 单个子代理全查。

**核心原则**：每个独立问题域派发一个子代理，让它们并发工作。

## 流程步骤

1. **切分问题域**：按"独立可并行"标准把任务分组成若干派发单；每单一个子代理。
2. **精确构造派发单**：子代理不继承你的会话上下文——派发单要自包含：
   - 任务的完整描述与验收标准；
   - 需要读的文件路径、需要遵守的规范（mgr / T1-T9 / 命名契约）；
   - 明确的返回格式：结论、证据（命令 + 输出摘要）、涉及文件清单。
3. **并行派发**：一次性派出全部子代理（flowforge 子代理体系支持并行派发）。
4. **结果汇总**：每个子代理返回后，核对证据再采纳结论；相互矛盾的结论先交叉验证再裁决。
5. **冲突回写**：两个并行子代理改了同一文件 → 让先完成者落地，后者基于新 HEAD 重做（或串行重派）。

## 门禁

- **独立性判定失败即中止并行**：发现任务间存在共享状态或先后依赖，立即改为顺序执行——并行只是手段，正确性优先。
- **不得为省事并行派发实现类任务到同一文件**：实现型并行仅限不同文件/模块（subagent-driven-development ④ 明确禁止并行实现子代理的冲突场景）。
- **结论必须有证据**：子代理的"成功/已完成"报告不等于事实——见 `verification-before-completion.md`（⑩）的代理信任条款。

典型自我合理化对照：

| 念头 | 事实 |
|---|---|
| "一个子代理全做了也一样" | 独立问题串行做浪费时间；每个子代理上下文更聚焦、成功率更高 |
| "派发单里贴上我的会话历史更好" | 子代理该拿它需要的，不是你经历过的；冗余上下文降低聚焦度 |
| "它们都报告成功了" | 逐个核对证据（diff、测试输出），代理报告不作数 |

## 与我方规范对接

- **对应状态机**：本资产服务 `implement` 阶段的任务并行编排，是 `subagent-driven-development.md`（④）在"任务独立"条件下的加速形态。
- **实现载体**：flowforge 的 `packages/subagent/*`（in-process / spawn / ff-sdk 多种驱动）提供子代理派发能力；其他 AI 工具使用其等价机制，方法论不变。
- **上下文保护**：并行派发单以文件而非粘贴长文传递（报告落文件、返回摘要），与本仓库"控制器上下文保持干净"的原则一致。
- **T1-T9**：并行子代理各自的验证证据独立留存，合并时统一归档到 `docs/process/verifications/`。
