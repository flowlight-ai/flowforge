# 缺陷协作规则（BUG_PROTOCOL）

> 本文件是**开发人员**与**测试人员**围绕 `docs/test/bugs.md` 协作的唯一规则来源。
> 目的：让双方通过 bugs.md 高效沟通、**责任边界清晰**、**问题不遗漏**、**不出现自证式关闭**。
> 适用范围：**本仓库**。规则与本仓库测试文档（`docs/test/README.md`）同级生效，冲突时以本文件为准。
> 版本：v1.1 ｜ 生效日期：2026-08-09

---

## 一、核心原则（四条铁律）

| # | 原则 | 说明 |
|---|------|------|
| **B1** | **谁发现，谁判定** | 缺陷是否真正修复，**只能由测试人员判定**。开发人员不得自行宣布"已验证/已关闭"。 |
| **B2** | **无证据不判定** | 任何状态推进都必须附**可复现命令 + 真实输出片段**。禁止仅凭读代码、仅凭单测、仅凭"我改了"就判定通过。 |
| **B3** | **不删不覆盖** | 工单**只增不删**。判定变化以追加历史记录体现，保留误判轨迹。编号一经分配永不复用。 |
| **B4** | **一因一单** | 一个根因一张工单。禁止把"N 个用例失败"压成一张票（会掩盖真实缺陷密度）。 |

---

## 二、字段所有权（**最重要**）

每张工单包含以下字段。**"归属"列决定谁有权修改该字段**，越权修改视为违规变更，回归时一律打回。

| 字段 | 归属 | 说明 |
|------|:----:|------|
| `ID` | 测试 | 形如 `P-42`，全仓唯一，永不复用 |
| `标题` | 测试 | 一句话描述现象 |
| `严重度` | 测试 | S1/S2/S3/S4，开发有异议请在「开发自述」中申辩，不得直接改 |
| `分类` | 测试 | 见 §六 |
| `文件:行号` | 测试 | 定位证据，**仓库根相对路径**（见 §五） |
| `现象` | 测试 | 实测现象 + 真实输出 |
| `建议修复` | 测试 | 仅为建议，开发可采用其他方案 |
| **`开发自述`** | **开发** | 开发填写：修复提交号、改动点、自测情况。**开发唯一可写字段** |
| **`测试回归结论`** | **测试（专属）** | 🔒 **仅测试人员可写**。开发人员任何情况下不得新增/修改/删除本字段 |
| `状态` | 测试 | 由「测试回归结论」联动，见 §三 |
| `T7/T8` | 测试 | 是否涉及铁律 T7（LLM 内容审核）/ T8（浏览器 DOM 验证） |

### 🔒 测试回归结论 字段格式（强制）

```
- **开发自述**：已修复，提交 `<commit>`，改用 shutil.which 校验 PATH
- **测试回归结论**：✅ Verified ｜ 回归日期 2026-08-09 ｜ 签署 QA
  - 复现命令：`python3 tests/test_cron_jobs.py --dry-run > /tmp/r.txt 2>&1; echo $?`
  - 实测输出：`📊 验证结果: 29 个任务, 5 个错误, 0 个警告` ／ 退出码 `1`
  - 判定说明：裸命令不再误报，PATH 校验生效
```

**判定枚举（仅测试可填）**：

| 标记 | 含义 | 联动状态 |
|------|------|----------|
| `⏳ 待回归` | 开发已自述修复，测试尚未验证 | `Fixed（待回归）` |
| `✅ Verified` | 测试实跑确认修复 | `Closed` |
| `❌ Rejected` | 实跑仍复现，或修复无效/空转 | `Open（回归打回）` |
| `⚠️ Partial` | 部分修复，仍有残留 | `Open` + 拆出新工单 |
| `🚫 Blocked` | 环境不具备（服务/浏览器未起），无法判定 | `Open（阻塞）` |

> **`Closed` 是测试人员的专属签名动作。** 开发人员把状态写成 Closed 的提交，一律回滚为 `Fixed（待回归）`。

## 三、状态机

```
   [测试新建]
        │
        ▼
      Open ──────────────┐
        │                │ 测试回归 ❌ Rejected / ⚠️ Partial
        │ 开发提交修复     │ （打回，允许多次往返）
        ▼                │
  Fixed（待回归）─────────┘
        │
        │ 测试回归 ✅ Verified（附证据）
        ▼
     Closed  ← 终态，仅测试可置
```

补充状态：
- `Open（阻塞）`：依赖服务/浏览器未就绪，测试标 `🚫 Blocked` 并写明缺失的前置条件。**阻塞不等于修复**，不得跳到 Closed。
- `Won't Fix`：需**开发在「开发自述」提出 + 测试在「测试回归结论」确认**，双方共识后方可置。

## 四、双方工作流

### 开发人员

1. 从 bugs.md 认领工单，提交信息格式：`fix(<scope>): <一句话> (P-xx) [<用户名>]`
2. 修复后**只做一件事**：在该工单下填写/更新 `开发自述`，写清提交号与改动点。
3. 把状态改为 `Fixed（待回归）`，然后**停手**——不要写「测试回归结论」，不要写 `Closed`。
4. 若对严重度/结论有异议，在 `开发自述` 中申辩，不要直接改测试字段。

### 测试人员

1. 收到修复后**真实运行**（服务真起、命令真跑、输出真贴），禁止只读代码。
2. 取退出码务必避开管道污染：用 `cmd > /tmp/x.txt 2>&1; echo $?`，**不要** `cmd | tail` 后取 `$?`。
3. 填写 🔒`测试回归结论`，联动 `状态`。
4. 回归中发现的**新问题另开新工单**，不塞进旧工单。
5. 更新 DI 仪表盘（§七）。

## 五、路径规范（强制，适用于全部测试产出）

**适用对象**：`bugs.md`、`bugs/` 明细、测试用例文档、测试报告、测试记录、复现命令、脚本与配置。

| 规则 | 要求 |
|------|------|
| **P1 一律相对路径** | 所有路径以**本仓库根**为基准书写，例如 `tests/test_foo.py:42`、`docs/test/bugs.md`。 |
| **P2 禁止绝对路径** | 禁止出现 `/home/<user>/...`、`/Users/...`、`C:\...`、`D:/...` 等任何机器相关绝对路径。 |
| **P3 禁止上跨仓库根** | 禁止 `../<其他目录>/...` 形式跨出本仓库根引用。跨仓依赖只描述**能力/接口**，不写对方文件路径。 |
| **P4 复现命令自包含** | 命令默认在仓库根执行，形如：<br>`python3 -m pytest tests/unit -q > /tmp/r.txt 2>&1; echo $?`<br>不要写 `cd /home/...` 前缀。 |
| **P5 临时文件除外** | `/tmp/...` 输出重定向属运行期产物，允许出现。 |
| **P6 引用原文例外** | 当缺陷本身就是"源码里写死了绝对路径"时，可原样引用该字符串作为证据，但必须包在反引号内并注明"（缺陷原文）"。 |

> 违反 P1–P4 的测试产出视为**不合规交付**，需修订后才计入交付物。

### 自检命令

```bash
# 扫描测试产出中的机器相关绝对路径（P6 例外需人工确认）
grep -rnE "(/home/[a-z]+/|/Users/|[A-Za-z]:[\\\\/])" docs/test/ | grep -v "缺陷原文"
```

## 六、严重度与分类

**严重度**

| 等级 | 判据 |
|------|------|
| **S1 阻断** | 服务/测试整套不可用；安全泄露；数据损坏 |
| **S2 严重** | 核心功能或质量受损；假通过（掩盖真实失败） |
| **S3 一般** | 明显缺陷但有绕过手段 |
| **S4 轻微** | 文档、命名、残留文件等 |

> **假通过（exit 0 掩盖失败、`|| true`、恒 `return 0`）一律不低于 S2** ——它会让所有其他缺陷失去可见性。

**分类**：`CI / 配置`、`安全隐患`、`T7 / T8 合规`、`单元测试失败`、`代码缺陷`、`测试脚本缺陷`、`文档不符`、`目录结构`、`验证阻塞（环境）`

## 七、DI 仪表盘（每次变更后必须重算）

```
DI = S1×10 + S2×5 + S3×2 + S4×1     （仅统计未关闭工单）
```

bugs.md 头部必须维护：缺陷总数、加权 DI、Open / Fixed待回归 / Closed 三态计数、按严重度与分类的分布表。

## 八、文件组织（缺陷量大时）

单仓缺陷超过 **40 条**时，`docs/test/bugs.md` 转为**索引**，明细拆分到 `docs/test/bugs/` 子目录：

```
docs/test/
├── bugs.md                 # 唯一主索引：DI 仪表盘 + 工单一览表 + 指向明细的链接
├── BUG_PROTOCOL.md         # 本文件
└── bugs/
    ├── S1-blocking.md              # 按严重度切分，或
    ├── <module>.md                 # 按模块/分类切分，或
    └── regression-YYYY-MM-DD.md    # 按回归轮次切分
```

规则：
- `bugs.md` **永远是唯一入口**，任何明细文件都必须在索引表中出现，否则视为遗漏。
- 明细文件内工单格式与 §二 完全一致。
- 编号全仓连续（不因分文件而重排）。
- 明细文件链接使用相对路径，形如 `bugs/regression-YYYY-MM-DD.md`。

## 九、防遗漏检查表（每轮回归收尾必过）

- [ ] 本轮所有 `Fixed（待回归）` 工单都已给出 ✅/❌/⚠️/🚫 判定，无遗留 `⏳`
- [ ] 每条 ✅ Verified 都附了**可复现命令 + 真实输出**
- [ ] 回归中新发现的问题都已**另开新工单**并纳入索引
- [ ] DI 仪表盘数字与工单实际状态一致（可用 §十 脚本核对）
- [ ] 索引表工单数 == 明细文件工单数之和
- [ ] 无「开发自行 Closed」的越权变更
- [ ] 环境阻塞项已写明**缺失前置条件**，未被误判为通过
- [ ] 全部测试产出通过 §五 路径规范自检

## 十、一致性自检脚本

```bash
# 在仓库根执行
# 1) 三态计数
grep -oE "状态\*\*：[^｜]*" docs/test/bugs.md docs/test/bugs/*.md 2>/dev/null \
  | sed 's/.*状态\*\*：//; s/（.*//' | sort | uniq -c

# 2) 工单总数（应与索引表行数一致）
grep -hcE "^### P-" docs/test/bugs.md docs/test/bugs/*.md 2>/dev/null

# 3) 找出「已 Closed 但缺测试回归结论」的越权关闭
awk '/^### P-/{id=$2; ok=0} /测试回归结论/{ok=1} /状态\*\*：Closed/{if(!ok) print "越权关闭:", id}' \
  docs/test/bugs.md docs/test/bugs/*.md 2>/dev/null

# 4) 找出编号重复
grep -hoE "^### P-[0-9]+" docs/test/bugs.md docs/test/bugs/*.md 2>/dev/null \
  | sort | uniq -d

# 5) 路径规范自检（§五）
grep -rnE "(/home/[a-z]+/|/Users/|[A-Za-z]:[\\\\/])" docs/test/ | grep -v "缺陷原文"
```
